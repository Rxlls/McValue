# McValue · 麦当劳套餐组合优化与点餐审计

基于**麦当劳官方 MCP** 的点餐决策助手。两个核心模式：

1. **套餐优化** —— 给定预算、人数、必选类别、口味与营养偏好，枚举候选组合，**逐个送官方 `calculate-price` 核价**，再按官方金额排序。
2. **点餐审计** —— 核验已有点餐清单的真实价格，在**同一门店、同一用餐方式**下生成替代方案，逐字段比较差异。

> 第一版**默认关闭真实下单**，全程只读。链路终点是官方核价，不是支付。

---

## 目标用户

| 用户 | 痛点 | 本项目的价值 |
| --- | --- | --- |
| **凑单的上班族** | 只想快点点完，又怕凑不满足够满减/用不上券 | 给定预算与人数，直接给出核过价的组合，并说明券是否真的生效 |
| **多人拼单的同事/同学** | 各人想吃的不一样，AA 算不清，主食饮料常常配不齐 | 按人数配齐主食与饮料，多个风格方案（最省/最均衡/最丰富/最多样）供挑 |
| **带孩子的家庭** | 关注份量与口味，怕点少了不够吃、点多了浪费 | 份量模型优先于价格，主动提示"可能吃不饱" |
| **习惯看账单的人** | 小程序上的价格和实际结算价常对不上 | 点餐审计：逐项核价、生成同门店同用餐方式的替代方案、解释每一笔差异 |
| **需要留痕的场景** | 报销、团建结算、部门订餐需要可核对的单据 | 审计报告含明细、优惠、配送费、数据来源与约束复核结果 |

**不适合**：跨门店比价、跨用餐方式（到店/外送）比价、代下单支付。前者官方数据不可比，后者本项目默认不做。

### 三条不可逾越的红线

1. **本地估算 ≠ 官方核价**。估算只用于剪枝与挑选送核价的候选；UI 上「本地估算」「核价成功」「核价失败」三种状态始终分开显示。
2. **未穷举不说最优**。`completeness === "bounded"` 时结论固定写作「已检查候选中的最优方案」。
3. **不同条件不比价**。门店 / `orderType` / `beType` / `beCode` / 预约时间任一不同，审计只输出「不可比」，不给差价结论。

### 预算是上限，不是目标：份量（饱腹）模型

只按「预算 + 必选类别」建模会产出荒谬方案。需求「2 个人，预算 60 元，要汉堡和饮料」曾给出
「麦香鱼 ×1 + 纯悦 ×1」（¥30）——它满足预算，也满足「有汉堡、有饮料」，但两个人根本吃不饱。
根因是评分把「越便宜越好」当成了目标函数（`budgetFit = 100 × (1 - 预算占用率)`）。

修正后的模型（`src/domain/satiety.ts`）：

- **份量折算**：按类别把商品折成「人份」——汉堡/套餐/早餐 = 1.0，小食 = 0.35，饮料 = 0.3，甜品 = 0.2。
  「2 个汉堡 + 2 杯饮料 = 2.6 人份」而「1 个汉堡 + 1 杯饮料 = 1.3 人份」，后者不够 2 人吃。
- **份量是硬约束**：`总人份 ≥ 人数 × minSatietyPerPerson`（默认每人 1 份），不足直接淘汰。
- **必选类别按人数配齐**：说「要汉堡和饮料」且 2 人 → 汉堡 ≥ 2、饮料 ≥ 2（显式说「要 1 个汉堡」则以用户为准）。
- **评分权重重排**：份量 0.30 > 口味 0.22 > 多样性 0.18 > 预算 0.15 > 营养 0.10 > 套餐 0.05；
  预算内即满分，不再奖励更便宜，只对「过度节俭」轻微扣分。
- **排序主键改为综合评分**，价格只作同分时的次要键（原来是按核价金额升序，等于稳定推荐最便宜的方案）。
- **预算不够时会明说**：无解时给出「按菜单最低价估算，让 N 人吃饱至少需要 ¥X」，并标注这是本地估算。

**诚实边界**（务必保留）：

- 份量是**启发式**模型，只用「这是汉堡 / 这是饮料」的分类常识，不代表任何官方营养口径。
- 真实热量只在官方营养数据完整覆盖时作为参考展示，缺失时明确写「热量参考不可用」，
  绝不拿估算值冒充官方数据，也不把参考热量当硬约束。
- 分类无法识别的商品保守计 0 人份，并在 UI 提示「N 件商品分类未识别，未计入份量」。

### 用餐结构：系统不确定时应当询问，而不是替用户决定

「2 个人」不等于「2 个汉堡 + 2 杯饮料」。现实里同样两个人可能是：

| 说法 | 结构（主食/饮料/小食/甜品） |
| --- | --- |
| 「2 个人，要汉堡和饮料」 | 2 / 2 / 0 / 0（按人数推算，UI 标 `derived`） |
| 「我们俩喝一杯就行」 | 2 / 1 / 0 / 0 |
| 「一个汉堡两杯饮品其他是小吃」 | 1 / 2 / 2 / 0 |
| 「要套餐和饮料」 | 2 / 2 / 0 / 0（主食锁定为套餐分类） |

因此数量不再由 `people` 机械相乘，而是收敛成一个显式的 `MealStructure`
（`main` / `drink` / `side` / `dessert` + `derived` 标记）：

- **能读出用户原话就听原话**：支持中文数字（「一杯」「两杯」）、并列需求（「可乐和汉堡」）、
  「喝一杯就行」这类隔句修正。
- **读不出就按人数给默认值，并在 UI 上标注「数量按人数推算，可修改」**，同时提供
  一人食 / 双人标准 / 双人分享 / 主食少·小食多 四个预设。
- **用户主动少点时不阻拦**：份量下限取 `min(人数所需, 结构折算份量)`，
  只在提示里写「该结构折算 X 人份，可能吃不饱」，不因此拒绝生成方案。
- **单位要按类别区分**：主食论「个/份」、饮料论「杯」，否则「汉堡两杯饮品」会把饮料的量算到汉堡头上。

### 方案要有多样性，不是最优点的邻居

只按综合分排序会输出一堆「同结构换饮料」的变体——看起来 5 个方案，其实 1 个。
现在：

- **核心结构指纹（忽略饮料）** 用于去重，只换饮料不算换方案。
- **风格分组**：最省 / 最均衡 / 最丰富 / 最多样，每种挑一个，且彼此结构不同。
- **送核价前先去重**：一半按综合分、一半按估算价取样，避免「最省」这一档拿到并不便宜的方案。

### 点名商品：强偏好，不是硬约束

说「要两杯可乐」，系统会识别 `可乐` 并优先匹配（结论里写明「已优先匹配你点名的：可乐」）。
但不设成硬约束——门店没这个商品时直接无解，比给一个合理替代更糟。

### 约束冲突：自动放宽最软的一条并说明

预算与份量是硬的，饮料杯数是最容易让步的。当原约束无可行组合时，
系统会自动把饮料减一杯重试，并在结论第一句写明「原约束下无可行组合，已自动把饮料从 2 杯放宽到 1 杯」。
放宽也救不回来时回滚，不假装方案满足原约束。

### 真实调用中发现并已处理的陷阱

- **随单购条件价**：`discountType` 以「随单购」开头的商品，菜单价需先买卡才生效。实测某套餐菜单价 ¥49.90，未购卡时官方核价 ¥114.50。本项目对这类商品一律用原价估算（见 `unitPriceForEstimate`）。
- **营养覆盖不全**：该门店 109 项可售餐品仅 56 项能匹配到官方营养库，聚合结果一律标注「已匹配 X/Y」，部分缺失时合计只作为**下界**。
- **券不一定适用**：券传入核价后若官方返回 `discount = 0`，标记为 `rejected` 并说明「无法确认生效」，不谎报优惠。
- **「汉堡」不能只按分类名死匹配**：真实菜单里分类名含「堡」的（巨无霸系列、安格斯厚牛堡）几乎都是高价四件套，
  而便宜的单人主食在「随心配 1+1」「精选单人餐」等套餐分类下。只按分类名匹配会得到
  「预算内凑不出 2 份汉堡」的假无解。因此「要汉堡」允许由套餐类等价满足（见 `SLOT_EQUIVALENTS`）。
- **混合分类必须按「具体语义」判**：「小食拼盘/多人餐」既含「小食」又含「多人餐」，
  若按套餐判，一份炸鸡会被当成一份主食，份量直接算错（实测把 1.95 人份算成 2.6）。
  现在按 `SLOT_PRIORITY` 具体到抽象排序，小食优先于套餐。
- **UI 勾选类别不能把数量写死**：`requiredCategories` 覆盖曾把 `minCount` 硬编成 1，
  2 个人勾「汉堡+饮料」会得到 1 个汉堡——这是「麦香鸡 ×1」的直接来源之一。

## 交易安全

第一版 `ENABLE_MCD_REAL_ORDER=false`，任何 `create-order` 调用都会被拒绝。若后续启用：

1. 必须持有成功的官方核价记录（金额非空）；
2. 到店场景必须选择 `takeWayCode`（取自 `calculate-price` 的 `takeWayList`）；
3. 用户须**逐项确认**门店、用餐方式、商品与数量、价格；
4. 确认令牌绑定订单指纹，任一关键字段变动即失效，必须**重新核价并重新确认**；
5. 令牌一次性且 10 分钟过期；
6. 创建订单 ≠ 支付成功；结果不明时先用 `query-order` 查状态，**不盲目重试**；
7. 取消订单需**单独授权**，不能沿用下单确认。

对应实现与测试：`src/order/guard.ts`、`tests/order-guard.test.ts`（13 项）。
